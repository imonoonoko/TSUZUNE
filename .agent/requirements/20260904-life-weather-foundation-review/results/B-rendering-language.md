# B — Rendering / language foundation

**Observation date:** 2026-09-04 (JST)  
**Scope:** source and isolated prototype review plus official documentation. This is a recommendation for a reversible spike, not approval to add a dependency, replace product rendering, or ship a native process.

**Integration status:** This packet is the pre-capability-probe assessment. The later hidden-Electron receipt in [`D-current-path-and-gpu.md`](D-current-path-and-gpu.md) supersedes its statements that adapter/device/replacement-device availability is unknown. That receipt still does not establish performance, visual superiority, or packaged-runtime parity. Its old 90-second same-score comparison is capability/pipeline-only; any backend adoption test must use the Living Archive Field score and the frozen protocol in [`../vertical-slice.md`](../vertical-slice.md).

## Current, verified boundary

- The connected renderer is `src/renderer/components/ObservatoryView.tsx`: TypeScript/React drives one `CanvasRenderingContext2D`, CPU-side hit testing, radial gradients and an animation loop. `src/core/observatory.ts` caps its observed field at **72** particles and deliberately keeps the particle interaction O(n²) below that ceiling. It is a source-level observation of the dirty checkout, not a packaged or installed-runtime claim.
- `work/archive-weather-prototype/` is a separate, product-unconnected **WebGL2/GLSL** work. `prototype.mjs` explicitly requests `webgl2`, draws point sprites and feedback textures, and optionally uses `EXT_color_buffer_float` / `OES_texture_float_linear`; it currently stops if WebGL2 is unavailable. It contains no Three.js, WebGPU, Rust, or WASM route.
- `package.json` pins Electron **43.2.0**, and Electron's release record says that build embeds Chromium **150.0.7871.129**. That is a strong platform precondition for WebGPU exploration, but it does **not** prove `navigator.gpu`, a usable adapter, required features, device recovery, or hardware acceleration on this PC. Those runtime facts remain unknown and must be probed in an Electron renderer.

The present code also establishes an important separation: the durable/meaningful part is the TypeScript data path and score (observations, source-backed phenomena, bounded field, privacy-safe snapshot); the rendering language only determines how those already-derived states become light, persistence, depth, and motion. A new language cannot by itself make the work more artful.

## Compatibility evidence (official, observed 2026-09-04)

- [Electron 43.2.0 release](https://releases.electronjs.org/release/v43.2.0) records Chromium 150.0.7871.129.
- [Chrome's WebGPU release note](https://developer.chrome.com/blog/webgpu-release) documents default WebGPU availability from Chrome 113 on supported Windows Direct3D 12 devices. This supports exploration in Electron 43, while preserving the per-device condition.
- [WebGPU](https://www.w3.org/TR/webgpu/) and [WGSL](https://www.w3.org/TR/WGSL/) are the current GPU-for-the-web and shading-language specifications. The WGSL publication is still a Candidate Recommendation Draft; do not treat the API surface as a zero-maintenance promise.
- [Khronos WebGL 2.0](https://registry.khronos.org/webgl/specs/latest/2.0/) is the direct API used by the isolated prototype.
- [Three.js WebGPURenderer](https://threejs.org/manual/en/webgpurenderer) documents a WebGPU-first renderer with a WebGL2 fallback and TSL translation to WGSL/GLSL, but also labels the renderer experimental and excludes legacy `ShaderMaterial` / `RawShaderMaterial` and `EffectComposer` migration paths.
- [wgpu's official crate documentation](https://docs.rs/wgpu/latest/wgpu/) says its WASM target is layered over browser WebGPU/WebGL2; [Rust and WebAssembly](https://rustwasm.github.io/book/) documents the required Rust/WASM/JavaScript workflow and glue. WASM therefore does not bypass browser-GPU compatibility.
- [Electron utility processes](https://www.electronjs.org/docs/latest/api/utility-process) are child-process infrastructure, not an embedded native GPU canvas. A native/sidecar renderer would add an IPC, lifecycle, packaging, and capture/embedding problem that is not present in the current product surface.

## Recommendation

Adopt **TypeScript for the source/provenance model and scheduler; direct WebGL2 with small, explicit GLSL passes for the isolated artistic surface** as the next reversible vertical slice. Preserve Canvas 2D for the existing in-app observation route and reduced-motion/static fallback. Do not import Three.js, Rust/WASM, or a sidecar for that slice.

This is not an assertion that WebGL2 is inherently more artistic than WebGPU. It is the lowest-risk path with actual project evidence: the isolated prototype already realizes the desired materials, while the current product remains a simple 72-particle Canvas 2D surface. The decisive thing to evaluate is whether a source-backed 90-second score produces legible recurrence, formation, rupture, and residual history without inventing relationships—not which API name appears in DevTools.

### Strongest counterargument

Electron 43 embeds Chromium 150, and Three.js offers a WebGPU-first / WebGL2-fallback renderer. A raw WebGPU or Three.js route may let a compute-backed field and postprocessing pipeline scale more cleanly than the prototype's JavaScript-to-WebGL buffer uploads, while avoiding a permanent GLSL-only ceiling.

That argument is credible, but not yet sufficient: WebGPU availability on this actual Windows renderer, loss/recovery, visual parity, and measurable advantage are all unknown; Three.js adds a dependency and its documented experimental/migration limits collide with the prototype's custom shader and feedback composition. The counterargument wins only if the bounded spike below produces a materially better source-grounded result or a measured budget win that direct WebGL2 cannot reach.

## Smallest benchmark / spike (no product change yet)

Create one **isolated, no-dependency renderer spike** from the current privacy-safe snapshot and the existing WebGL2 prototype; do not wire it into `src/`, the active Vault, or packaging.

1. **Capability receipt first.** In a real Electron 43 renderer window, record only `process.versions`, WebGL2 availability/extensions, `Boolean(navigator.gpu)`, `requestAdapter()` success, adapter limits/features needed by the spike, and a WebGPU device-lost outcome. Treat a false/failed result as a clean stop for WebGPU, not a reason to enable flags or add a native route.
2. **Same score, two backends.** Keep the current opaque snapshot, seed, 90-second score, source-event ordering, canvas size, DPR cap, pause/reduced-motion semantics, and hover label identical. Compare the existing WebGL2 renderer with a minimal raw-WebGPU implementation containing only (a) particle/light draw and (b) one feedback/history pass. Do not add a scene graph, compute simulation, Three.js, Rust, or a product API in this spike.
3. **Collect two kinds of evidence.** Capture 0/30/60/90-second frames plus visibility pause/resume and context/device-loss behavior. Measure each backend's frame interval distribution, allocated canvas/texture dimensions, and errors on the same PC; label these measurements machine-specific, not general performance claims. Separately conduct a blind, source-aware visual review: can the viewer distinguish source-derived event progression from decorative/random motion, and does either backend enable a material distinction the other cannot express within the same frame budget?

**Success condition:** WebGPU is selected for a later slice only if it initializes and recovers on this renderer *and* provides either a visibly necessary source-grounded material/pass or a repeatable measured budget advantage. Otherwise keep the direct WebGL2 foundation. **Stop condition:** no WebGPU adapter/device, device-loss failure, no artistic distinction, or no measured advantage; retain Canvas 2D and the existing WebGL2 prototype without broadening scope.
