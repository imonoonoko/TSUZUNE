# AI再利用の読取・根拠契約 — 要件

設計日: 2026-09-06 JST。依頼: 「AIと再利用するまで出来ている。ただちゃんとノートが使われているかは分からない」への基盤レビューを受け、具体的な設計へ進む。

## 目的と完了境界

AIが通常の質問から必要なノート本文へ到達し、時点と制約を保って回答し、人間が主要な主張の根拠へ戻れる状態を定義する。モデル内部で何を因果的に利用したかは観測対象にできない。「適切に使えた」は、取得した原文が回答の主張を支え、必要な条件を落としていないことで評価する。

今回の成果は要件・変更箇所・受入ケースを揃えた設計。製品コード、Skill、MCP登録、本番binaryの変更や評価実行は含まない。現在の実行状態と次の一手は [PLAN.md](../../../PLAN.md#current-decision) 一箇所に置く。

## 利用者に返す形

通常は結論に、根拠となるノートへのリンクと必要な時点・未確認事項を添える。毎回レシート表や全tool履歴を読ませない。根拠確認を求められた時だけ「主要な主張／取得した原文の該当箇所／出典とrevision／未収録・不明」を展開する。revisionは読取証跡用で、通常の説明へ露出させる必要はない。

例: 「灯台の現行モデルは灯モデルです。8月20日からの採用記録が根拠です［該当ノート］。品質判定には固定12枚の比較が必要です［判定ノート］。」ノートの索引だけを読んだ段階では、この結論を確定しない。

## 成功条件

1. **到達と読取**: 質問に必要な本文を取得できる。検索結果、索引、節選択、文字数切断を全文読取と混同せず、不足に応じて追加取得する。
2. **回答の整合**: 主要な主張が実際に取得した本文で支持される。現行と過去、採用と候補、制約と例外を取り違えない。資料で決められない点は決められないと答える。
3. **追跡と観測境界**: 主張から出典へ戻れる。サーバーのContext収録と、回答側で検査した根拠対応を別の事実として扱う。代表ケースで合否と原因を判定できる。

## 必須要件

| ID | 要件 | 確認先 |
|---|---|---|
| R1 | IDが不明なら自然文の質問から検索する。正解ノート名を評価実行者へ事前配布しない | E1〜E5 |
| R2 | Contextに必要本文とrevisionがある場合はその本文を根拠にできる。本文不足・現在性確認がある場合だけ追加取得する | E3等の追加取得判定。C1〜C4は表示情報の確認まで。条件未成立ならR2未検証 |
| R3 | 過去を問う質問は過去の記述へ、現行を問う質問は確認できる現行の記述へ戻る。mtimeの新しさだけでは採用判断を上書きしない | E1、E2、E5 |
| R4 | 主要な事実・判断・制約を出典の該当箇所と対応付ける。引用の存在だけでは合格にしない | 全Eケース |
| R5 | 必要な根拠がない・矛盾が解けない場合に、推測の採用や「全Vaultに存在しない」の断定をしない | E4、E5 |
| R6 | 読取中に同一IDのrevisionが変わった場合、異なる版の本文を連結しない | 実callerの版変更応答への対処。既存fetch回帰・隔離MCP検証だけでは未検証 |
| R7 | `usage_receipt`の未観測fieldを、AIの自己申告からobservedへ変えない | schema回帰、回答監査 |

## 方針と対象外

既存のMarkdown、検索、fetch、Context Compilerを使う。ノートの存在、候補に入ったこと、Contextへの収録、根拠に沿った回答はそれぞれ別の段階である。必要な部分まで読めたかと、不要な追加取得があるかを見て改善を選ぶ。

新DB、vector検索、embedding、全Vault投入、常駐Agent、Hook、利用ログの永続蓄積、回答を作る内蔵AIは設けない。検索順位・候補枠・本文予算の変更は、該当原因が確定してから別sliceにする。一般ノートへのState metadata強制やMOC全文展開も含まない。
