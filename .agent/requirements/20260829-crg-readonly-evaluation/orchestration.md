## Inputs already established

- Archimedes pressure-tested the adoption claim and defined the strongest counter-hypothesis: current `rg` plus adaptive exploration may outperform a stale or incomplete graph once setup and false-negative risk are counted.
- Zeno audited official CRG 2.3.8 claims and confirmed the benchmark caveats, 33% flow recall limitation, 30-tool surface, tool filtering, incremental parsing, and embedding/security boundaries.
- Faraday mapped the current TSUZUNE repository fit and proposed the three representative TypeScript change paths.

These are inputs, not completion evidence. The current run must independently execute and score the tool.

## Packet ownership

- Packet 01: a read-only repository auditor owns exact direct-reference ground truth in current `src` and `tests`. It cannot run CRG, edit files, change the frozen scoring rule, or write TSUZUNE.
- Packet 02: the parent owns the disposable tracked snapshot, pinned Python environment, CRG build/query/update commands, raw evidence reduction, and source-checkout safety checks.
- Packet 03: an independent reviewer owns arithmetic, expected-set comparison, unseen-boundary checks, and whether the decision follows the predeclared kill criteria. It cannot rerun with relaxed criteria or edit product/Vault files.
- Packet 04: the parent owns final integration, workflow verification, and the single final-boundary TSUZUNE writeback when the canonical decision changes.

All agents share the repository and are not alone in the codebase. They must preserve unrelated changes, never revert another worker, and stop rather than expand into product implementation, MCP registration, Hooks, daemon, embeddings, or package changes.

## Decision rule

- **Advance to 10–20 A/B:** isolated build and refresh work; all three cases have no critical false negatives; CRG provides non-duplicative structural context beyond exact `rg`; and measured setup/query overhead is plausible for amortization across repeated tasks.
- **Return to Held:** any critical false negative, unsupported test/caller relation that prevents safe routing, build/freshness failure, or overhead with no demonstrated context advantage.
- A passing Gate 0 authorizes only the next measured A/B design. It does not authorize installation, MCP registration, production wiring, Hooks, daemon, embeddings, or product implementation.
